# S7. Compliance Considerations

AI-assisted Salesforce development introduces compliance considerations that do not exist in traditional development. When customer data appears in prompts, when code is generated by a third-party model, and when deployment workflows change, compliance requirements may apply differently. This chapter covers HIPAA, SOC 2, GDPR, and Salesforce Security Review considerations.

## Data in AI provider logs

When you paste Salesforce content into an AI tool prompt, the content is sent to the AI provider. What the provider does with it matters for compliance.

**What may be logged:**
- Prompt content (the text you paste)
- Generated code (what the AI produces)
- Account information, record IDs, field values from SOQL queries you paste
- Error messages that contain stack traces with internal paths

**Provider policies vary:**
- Anthropic (Claude): does not use customer data for training by default, has data retention policies
- OpenAI (ChatGPT): has data policies that vary by plan (Business/Enterprise have better data controls)
- GitHub Copilot: has specific data handling policies for GitHub Enterprise

**The compliance implication:**

If your org contains HIPAA-regulated data, and a developer pastes a SOQL query with that data into an AI tool, the data may be in the AI provider's logs. This is a potential HIPAA violation if the provider is not a Business Associate under HIPAA.

Always assume: anything you paste into an AI tool prompt may be logged and may not be under your control after that point.

## HIPAA-specific considerations

If you work with Protected Health Information (PHI):

```
HIPAA requirements for AI-assisted Salesforce development:
1. Never paste PHI into AI tool prompts (names, diagnosis codes, treatment records, any health information)
2. Use scratch orgs with synthetic/test data for AI-assisted development
3. Ensure the AI provider's Business Associate Agreement (BAA) covers the data handling if PHI will appear in prompts (unlikely to be covered)
4. Document your AI tool usage in your HIPAA policies and procedures
5. Audit AI tool usage for PHI exposure (check prompt logs if available from your AI provider)
```

PHI can appear in unexpected places: Account names for healthcare organizations, custom objects with health data, Opportunity names that describe medical procedures. Be rigorous about what you paste.

## SOC 2 considerations

SOC 2 compliance focuses on data security, availability, processing integrity, confidentiality, and privacy. AI tool usage creates new vectors:

```
SOC 2 controls for AI-assisted Salesforce development:
1. AI tool access to Salesforce orgs: ensure only scratch orgs are accessible (S2 org isolation)
2. AI-generated code review: ensure AI-generated code is reviewed before deployment (S5)
3. Change management: AI-generated code must go through the same change management process as human-written code
4. Audit trail: log who used AI tools, when, and what code was generated (S8)
5. Vendor risk: understand your AI provider's SOC 2 status and data handling policies
```

SOC 2 auditors may ask about AI tool usage. Be prepared to document:
- Which AI tools are used
- What orgs they have access to
- The review process for AI-generated code
- The permissions configuration preventing production access

## GDPR considerations

If you work with EU resident data:

```
GDPR considerations for AI-assisted Salesforce development:
1. Data minimization: do not paste EU resident PII into AI tool prompts (names, emails, addresses)
2. Right to erasure: if PII appears in AI provider logs, the erasure request may not be fulfillable
3. Data processing agreements: your AI provider may need a Data Processing Agreement (DPA) if you process EU resident data
4. Transfer mechanisms: ensure your AI provider's data handling for EU data complies with Schrems II requirements
```

The practical implication: treat AI prompts as if they are a third-party system processing personal data. Minimize what goes in. Assume it may be retained.

## Salesforce Security Review and AI-generated code

If you are building a managed package for the Salesforce AppExchange, your code must pass the Salesforce Security Review. AI-generated code has specific considerations:

```
Security Review considerations for AI-generated code:
1. All AI-generated code must pass the same Security Review as human-written code
2. FLS enforcement, CRUD checks, SOQL injection prevention: all apply regardless of how the code was generated
3. The Security Review submission must disclose that AI tools were used in development (Salesforce may ask)
4. If AI-generated code is security-reviewed and approved, that approval covers the code at the time of review. Subsequent AI-generated additions must also be reviewed.

Key failure points in AI-generated code for Security Review:
- Missing WITH USER_MODE on DML
- Missing FLS checks (Schema.sObjectType.Field.isAccessible())
- SOQL injection via dynamic query without escaping
- Hardcoded credentials or secrets
- @AuraEnabled methods without authorization
- Unprotected sensitive data in logs
```

The reviewer-AI (sf-code-review skill) and security-AI phases of the multi-agent workflow are designed to catch these issues before the formal Security Review submission.
