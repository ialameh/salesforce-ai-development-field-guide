# P4. Prompts for Testing

Test code generated by AI often looks good (high coverage, compiles cleanly) but proves nothing. AI writes tests that assert execution happened, not that behavior is correct. This chapter covers how to prompt for tests that actually prove your code works, catch edge cases, and satisfy Salesforce security review requirements.

## The AI testing failure mode

AI generates tests that:
1. Assert that code ran without error (System.assert(true))
2. Use `seeAllData=true` which makes tests dependent on org state
3. Test the happy path and miss the failure paths
4. Do not test bulk behavior (200 records)
5. Do not test permission-restricted users
6. Do not test governor limit behavior under load

The result is a test class with 85% coverage that passes in CI and fails in production when a non-admin user runs the code.

## The non-negotiable test constraints

```
Must:
- Use @IsTest (not @testSetup decorator for modern Apex test structure)
- Use @testSetup only for data that all test methods need (and prefer creating data per test for isolation)
- Use seeAllData=false (default) for all tests unless explicitly testing a Flow or platform feature that requires it
- Use System.runAs() to test behavior as a specific user profile
- Test with 0, 1, and 200 records (bulk boundary tests)
- Assert on outcomes, not on implementation details
- Test the failure path: what happens when the external system returns an error, when FLS blocks access, when a record is locked

Must not:
- Use System.assert(true) or equivalent fake assertions
- Use seeAllData=true without a clear reason documented in the test
- Test implementation details (e.g., "assert this specific method was called" - test behavior, not implementation)
- Hardcode IDs (use Test.getStandardUserId() or @TestVisible setters)
- Use Test.isRunningTest() to skip production logic (move the test seam to @TestVisible instead)

Test structure:
- One logical assertion per test method (or a small group of related assertions)
- Descriptive test method names: testScenarioExpectedBehavior (e.g., testUpdateBillingAddressTriggersTaskCreation)
- Isolation: each test creates its own data, does not rely on data from other tests
- Bulk: testMethodScenarioBulk() for bulk behavior
```

## Test method prompts

```
You are developer-AI. Write test methods for <class name>.

Class: <name>
Testing context: <what the class does, how it is used>

Test methods to write:

1. Happy path test:
   - Setup: create test data for <object>
   - Execute: call the method being tested
   - Assert: verify <specific outcome> using System.assertEquals or System.assertNotEquals
   - Do not assert on record IDs or implementation details

2. Edge case: empty input
   - Setup: pass empty list (List<Account>)
   - Execute: call the method
   - Assert: verify early return or graceful handling (e.g., no exceptions thrown)

3. Edge case: partial failure
   - Setup: mock a failure scenario (e.g., Database.update with partial failure)
   - Execute: call the method with DML that fails for some records
   - Assert: verify success for valid records and error handling for failed records

4. Bulk test:
   - Setup: create 200 Account records
   - Execute: call the method with the 200-record list
   - Assert: verify all 200 processed (no governor limit failures)

5. Permission test (using System.runAs):
   - Setup: create a user without FLS access to one field
   - Execute: call the method as that user
   - Assert: verify error is handled gracefully (code does not crash, error is logged)

6. Error path test:
   - Setup: mock an external callout failure
   - Execute: call the method
   - Assert: verify exception is caught and handled appropriately (not thrown to user)

Mock strategy: Use HttpCalloutMock for external callouts. Use Test.startTest/Test.stopTest for async operations.

Write the complete test class.
```

## Example: testing a service method

```
Write AccountServiceTest for this method:
public static Database.SaveResult[] updateBillingAddress(List<Account> accounts, String newStreet, String newCity, String newState)

Test methods required:

1. testUpdateBillingAddressWithValidData:
   - Create 5 Account records with existing BillingAddress
   - Call updateBillingAddress with new address values
   - Assert that BillingStreet, BillingCity, BillingState updated on all 5 records
   - Assert that SaveResult success = true for all records

2. testUpdateBillingAddressWithEmptyList:
   - Call updateBillingAddress with empty List<Account>
   - Assert no exceptions thrown (early return behavior)
   - Verify no DML statements executed

3. testUpdateBillingAddressPartialSuccess:
   - Create 3 Account records
   - Mock Database.update to fail for record 2 (use Database.SaveResult with success=false)
   - Call updateBillingAddress
   - Assert records 1 and 3 updated, record 2 handled gracefully

4. testUpdateBillingAddressBulk200Records:
   - Create 200 Account records
   - Call updateBillingAddress
   - Assert all 200 updated (no governor limit failures)
   - Verify SaveResult array has 200 entries

5. testUpdateBillingAddressUserWithoutFLS:
   - Create a community user profile (UserRole or Permission Set)
   - Remove FLS for BillingCity field for that user (FieldPermissions object)
   - Use System.runAs to run as that user
   - Call updateBillingAddress
   - Assert that the code handles FLS gracefully (either skips the field update or throws a typed exception)

6. testUpdateBillingAddressNullAddressFields:
   - Create Account with null BillingCity
   - Call updateBillingAddress with newCity = null
   - Assert that null newCity does not overwrite existing BillingCity (skip null fields logic)

Data creation: Use Test-data factory pattern (create a TestDataFactory class with @TestVisible methods). Do not hardcode IDs.
```

## Mock and stub prompts

AI often does not know the right mock pattern for Salesforce. Specify the pattern explicitly.

```
You are developer-AI. Write a test mock for <class>.

Mock type: <HttpCalloutMock / StaticResourceCalloutMock / custom mock interface>

Requirements:
- HttpCalloutMock: implement HttpCalloutMock interface, return HttpResponse with status 200 or error status as needed
- StaticResourceCalloutMock: load test data from a Static Resource (create a JSON file in the test static resource)
- Custom mock: for interfaces or classes with virtual methods

Mock for ErpIntegrationService:
- Use a mock that implements the same interface as ErpIntegrationService callout methods
- Return success for normal test cases
- Return error response for failure path tests
- Track call count so you can assert the callout was made the correct number of times

Write the mock class and the test methods that use it.
```
